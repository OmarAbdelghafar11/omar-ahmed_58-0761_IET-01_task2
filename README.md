The notebook read 283 lines from `bookings.jsonl`. It quarantined 24 of them, which leaves 259 valid bookings. The quarantine reasons were: 4 invalid student ids, 4 totals that did not match the tickets, 3 unknown ticket types, 3 ticket quantities below 1, 3 bookings made on or after the event date, 3 duplicate booking_ids, 2 missing events and 2 bookings with no tickets. The duplicate check runs after validation so that only valid bookings can claim a booking_id. If it ran first, an invalid first copy would take the id, its valid re-send would be thrown away as a "duplicate", and we would lose a real booking under the wrong reason. In this file the counts would not change, because all three duplicates are exact copies of valid bookings, but on other data they could. The field that drifted is `promo_code`. It appears from 20 October 2026 on, and every earlier booking lacks it. The Pydantic model makes it optional with a default of `None`, so older documents still pass and get an empty value in `bookings`. The booking's `total` is not a column of `fact_ticket_sales` because the fact has one row per ticket entry, while `total` belongs to the whole booking. It would repeat on every ticket row of a booking, so `SUM(total)` over the fact would give 42,000 EGP instead of the real 31,285 EGP, because the 55 bookings with more than one ticket type would be counted more than once. Summing `amount` gives the correct revenue.
